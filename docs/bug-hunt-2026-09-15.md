# Eval bug hunt — 15 September 2026

Started from clean Eval commit `465ee3a`. This pass focuses on FEN validation, chess-rule edge cases, and PGN export. The original app data was backed up before testing; reproduction and verification artifacts are in `/tmp/eval-2026-09-15/`. AI source was unchanged. No UI layout changes were made.

## Reproduced defects and corrections

| Area | Reproduction | Correction |
| --- | --- | --- |
| FEN structure | Empty-square counts such as `80`, `08`, `44`, and a Unicode digit were accepted. Unknown/duplicate castling symbols and extra fields were silently accepted. | Validate ASCII counts and field structure before accepting the position. Failed validation preserves the previous board and last move. Existing abbreviated FEN input remains supported. |
| En passant | A FEN could identify d6 as an en-passant target with no black pawn on d5, a friendly pawn there, an occupied target, or an occupied source square. This could permit a capture of a nonexistent pawn. | Require the appropriate opposing pawn, an empty target, and an empty double-push source square. A valid target is still accepted when no capturing pawn is adjacent. |
| PGN notation | Importing `e2e4 e7e5 g1f3 b8c6` and exporting produced those coordinate strings instead of standard PGN algebraic notation. Castling, promotion, captures, and disambiguation had the same problem. | Replay the main game from its initial position and generate legal SAN, including promotion choice, disambiguation, check, and checkmate. Invalid stored movetext produces an export error rather than an invalid PGN. |
| Opening metadata in exports | Exploring `1. e4 c5` inside an `e4 e5 Nf3 Nc6` game caused the main-game PGN's Opening header to say “Sicilian Defense.” | Use the main game's supplied opening or derive its opening from the full main-game history. Sharing and clipboard export use the same code path; exploration does not change the exported game. Available preview scores are retained when deeper scores are absent. |

The initial nine targeted JVM cases had seven failures (`baseline-unit-tests.txt`). The two real-engine emulator workflows both failed before correction (`baseline-emulator-tests.txt`): one retained UCI move strings, and the other attached variation opening metadata to the main game. The export test intercepts the chooser intent and does not send anything. Its clipboard check restores the original clipboard afterward.

## Chess-rule cross-check

The castling and en-passant checks were reviewed against the [FIDE Laws of Chess](https://handbook.fide.com/chapter/E012023). SAN and FEN handling were cross-checked against [python-chess's implementation](https://raw.githubusercontent.com/niklasf/python-chess/master/chess/__init__.py). No third-party implementation was copied into the app.

Four positions from [Stockfish's move-generation test set](https://raw.githubusercontent.com/official-stockfish/Stockfish/master/tests/perft.sh) were measured independently with the installed Stockfish 19 executable. Eval's legal-move trees matched these reference totals:

| Castling/pins middlegame position | 3 | 97,862 |
| Rook/pawn endgame position | 3 | 2,812 |

The exact FENs and engine output are in `stockfish-perft-reference.json`; the cases are retained in `LegalMoveTreeTest`. Additional cases cover pinned en-passant captures, castling through check, underpromotion, SAN source-file/source-rank disambiguation, and checkmate notation. These checks validate the covered positions and input rules, not every possible legal or historically reachable FEN.
