Eval code audit

Date 28 September 2026 Code master @ 076ca73 plus uncommitted camera rework Size 77 Kotlin files, 27,361 lines; 64 test files Changes made none

Verdict

Eval’s foundations are better than its surface. The chess rules engine is correct under hard probes, state updates are race-free, the new import and scanning pipeline is carefully bounded and sandboxed, and the AI handoff escapes its data correctly. The problems cluster in a few places: two screens crash as soon as they open (the ECO opening list and Lichess TV), Lichess TV cannot load a game because a debug logger buffers the live stream, and in Manual analysis a move-list tap can show the previous position’s evaluation and keep it there.

Around those, the app leaks work in ways users feel: analysis runs on in the background, the whole UI recomposes on every engine update, several settings do nothing or lie about their values, and a share, a typo or a display checkbox can wipe a finished analysis. The release pipeline is broken (R8 fails), so the debuggable build is what users install. The test suite is large but mocks away exactly the layers where the worst defects live.

Most Critical and High items are small, local fixes. The structural work (engine protocol, storage, state shape, lifecycle) is a few weeks, and the remediation plan below orders it.

How it was checked

Seven area audits read every main-source file line by line: chess rules, engine pipeline, state and concurrency, network and import, security and privacy, UI, and export/settings/build/tests/docs. Their findings were merged, de-duplicated and re-rated on one scale. The lead auditor then re-checked the highest-impact claims against the code, the build and live services; those findings carry a “Re-verified” mark. “Confirmed” means the failure path was traced through the code or reproduced; “Plausible” means the code path is real but the trigger or impact was not demonstrated.

  • Build, unit tests, lint. assembleDebug, testDebugUnitTest and lintDebug on the working tree: build OK, 90 of 90 JVM tests pass, lint 0 errors and 94 warnings. Instrumented tests were not run (they need the emulator’s real app data and Stockfish).
  • Release pipeline. :app:minifyReleaseWithR8 fails on the missing com.gemalto.jp2.JP2Decoder. On a scratch copy with only the AGP-generated -dontwarn rule added, R8 completed and its mapping.txt was inspected (BLD-1, BLD-2).
  • Live streaming. A Java probe with the exact OkHttp 4.12.0 jars against a live Lichess TV game: 227 ms to first line without the body logger, still blocked at the 20 s cap with it. Lichess keeps the NDJSON stream open and adds moves as they are played (NET-1).
  • Lichess API shape. Checked live: api/game/{id} has no pgn; the TV channels returned the same game for “best” and “bullet”; both explorer endpoints return 401 (NET-1, UI-2, NET-2).
  • Bundled data. eco_codes.json: 2,010 entries, 500 distinct ECO codes (UI-1).
  • Chess probes. The chess auditor compiled the chess sources alone: 18 perft positions, 175,459 SAN round-trips and full ECO replay, plus the illegal-FEN and PGN edge cases (CHS-*).
  • Engine protocol. The engine auditor drove Stockfish 19 directly: readyok preceded the old bestmove in 20 of 20 mid-search trials, an illegal FEN made it exit, and a coroutines 1.7.3 probe showed the reader’s timeout not firing (ENG-1, ENG-2, CHS-1).
  • Emulator (read-only). One auditor used adb shell run-as to read the preferences size (77 KB per analysed game) and to query the installed engine’s options (No such option: Use NNUE). Nothing was written.

Stockfish & analysis

ENG-1?High

Tapping a move during Manual analysis shows the previous position’s evaluation, and the display then stays one position behind

ConfirmedRe-verified by lead auditor
stockfish/StockfishEngine.kt:452-491 · stockfish/StockfishEngine.kt:275-289 · stockfish/StockfishEngine.kt:298-339 · ui/AnalysisOrchestrator.kt:579-597 · ui/BoardNavigationManager.kt:61 · ui/BoardNavigationManager.kt:104 · ui/BoardNavigationManager.kt:134 · ui/GameContent.kt:972
Defect
startAnalysis cancels the old reader, sends stop, waits for readyok, sends the new position and go, then reads until the next bestmove. Stockfish answers isready immediately, even while the old search is still unwinding, so the old search’s final info lines and its bestmove arrive after readyok. They are parsed as output for the new FEN, and the reader stops at the old bestmove. The restartAnalysisAtMove path is safe because ucinewgame waits for the search to finish; analyzePosition (move-list taps, variation navigation) has no such barrier.
Impact
In Manual after 1.e4, while the depth-32 search runs, tap “1…e5”. The card shows the old position’s −0.2 with the principal variation “e7-e5 g1-f3…” starting from an empty square, and arrows point e7→e5. The result carries the new FEN, so the position check passes. The ensure loop already has its first result, so the display never updates while the real search burns 4 threads to depth 32 unread; each later tap shows the previous position’s analysis.
Fix
Track an in-flight search and, when one is running, send stop and drain until bestmove before isready; or join the previous reader so it consumes its own bestmove. Add a fake-engine test that navigates mid-search and checks that the principal variation is legal on the current board.
Evidence
The engine auditor ran stop + isready against Stockfish 19 mid-search: readyok preceded the old bestmove in 20 of 20 trials, and the reader then received the old position’s multipv 1..3 lines. The lead auditor traced the same order in startAnalysis and waitForEngineReady.
ENG-2?!Medium

readLineWithTimeout can’t actually time out, and drops the line that arrives late

Confirmed
stockfish/StockfishEngine.kt:341-356 · stockfish/StockfishEngine.kt:186-205 · stockfish/StockfishEngine.kt:307 · stockfish/StockfishEngine.kt:638-648
Defect
withTimeoutOrNull { runInterruptible { reader.readLine() } } relies on Thread.interrupt(), which does not unblock a read on a process pipe. The timeout therefore waits for the read to finish, and because the coroutine was cancelled meanwhile, the line that finally arrives is discarded.
Impact
When a Stockfish iteration takes more than 3 s (measured gaps of 3.1–7.7 s at 1 thread), the multipv 1 line of that depth is lost while lines 2 and 3 are kept, so the card shows “Depth N” with a depth N−1 best line that can rank below line 2. The AI engine-lines handoff can lag several depths. The ready and idle timeouts never fire against a silent engine, and restart() would hang holding lifecycleMutex if a bestmove were ever missed.
Fix
Read the process output on one dedicated thread into a Channel<String> and receive from it with withTimeoutOrNull; in restart/shutdown, destroy the process first so EOF unblocks the reader.
Evidence
JVM probe with the project’s coroutines 1.7.3: a 300 ms timeout returned null after 2,004 ms and the line was lost; a plain interrupt of a blocked readLine had no effect for 3,007 ms.

Strengths

Worth keeping as the code changes; several of these are the reason the fixes above are small.

Chess core is correct where it counts

Move generation matched all 18 perft probe positions (castling rights, pinned en passant, promotions, double check). 175,459 SAN round-trips produced 0 failures, and all 2,010 ECO entries replay to their keyed FEN.

State updates are atomic

All 64 state writes use _uiState.update {}; there is no read-modify-write, no GlobalScope, and the ViewModel holds only the Application context. Game loading uses generation tokens, with race tests.

Score perspective is right everywhere

Side-to-move → White conversion is correct in the stages, eval bar, principal variations, AI handoff and export; mate-in-0 keeps its sign, with tests. CompletedPvIteration handles Stockfish’s mixed-depth MultiPV output.

The engine is a good citizen on the CPU

Stockfish runs under nice -n 10 with threads capped to the CPU count, a fix that came out of an earlier ANR investigation.

WebViews are well sandboxed

No addJavascriptInterface anywhere. The recognizer blocks network loads and file/content access and has a CSP; the scanner is HTTPS-only, blocks mixed content and refuses SSL downgrades.

The new import pipeline is bounded

ChessDocumentReader caps entries (512), total size (32 MB) and part size (8 MB), blocks zip-slip, rejects XML DOCTYPEs and caps RTF nesting. Bitmaps are bounds-checked and sampled.

AI handoff escaping is correct

Plain values are XML-escaped exactly once, the FEN is JSON-quoted inside the board script, placeholders come only from templates, and the intent is explicit.

Settings import validates before writing

Shape, numeric range and catalogue checks run before one atomic apply; game-storage keys are protected, with many negative tests.

Network and secrets hygiene

Cleartext is disabled, only system CAs are trusted, and no secrets or keystores appear anywhere in the git history.

Board setup is exemplary UI

Saveable state with a custom Saver, semantic squares with click actions, selectable/toggleable rows, and gestures that yield to the page scroll.

Careful engineering habits

Dated bug-hunt notes in docs/ record reproductions, fixes and verification. The GIF encoder is a faithful port with per-frame rendering and cancellation.
